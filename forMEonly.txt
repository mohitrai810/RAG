# 1. First: What are we actually building?

Our end goal is:

> A system where a user can give us documents, we index those documents, and later ask questions whose answers are generated from the relevant parts of those documents.

For example, imagine we have:

```text
redis.md
```

containing:

> Redis AOF records write operations and can reconstruct the dataset after restart.

The user asks:

> "How does Redis recover after a restart?"

A normal LLM might know the answer from its training data—or might hallucinate.

Our RAG system instead does:

```text
User Question
      ↓
"How does Redis recover after restart?"
      ↓
Convert question → embedding
      ↓
Search PostgreSQL/PGVector
      ↓
Find relevant chunks
      ↓
Give chunks to LLM
      ↓
LLM generates answer
      ↓
Answer + sources
```

That is **Retrieval-Augmented Generation**.

---

# 2. There are actually TWO major pipelines

This is the most important thing to understand.

A RAG system isn't just one pipeline.

It has:

## Pipeline A — Indexing

This happens when we add documents.

```text
Document
   ↓
Load
   ↓
Extract text
   ↓
Clean/normalize
   ↓
Chunk
   ↓
Embedding
   ↓
Store in PostgreSQL + PGVector
```

## Pipeline B — Querying

This happens when the user asks a question.

```text
Question
   ↓
Embedding
   ↓
Vector search
   ↓
Relevant chunks
   ↓
Context construction
   ↓
LLM
   ↓
Answer
```

We spent today's work preparing the **middle of Pipeline A**.

# 11. Why do we have `content_hash`?

THIS is a production-oriented decision.

Imagine the user uploads:

```text
redis.md
```

today.

Then uploads the exact same file tomorrow.

Without a hash:

```text
redis.md
redis.md
redis.md
redis.md
```

We might repeatedly:

```text
chunk
 ↓
embed
 ↓
store
```

That's wasteful.

Instead:

```text
Document
   ↓
SHA-256
   ↓
content_hash
   ↓
Does this already exist?
```

If yes:

```text
already indexed
     ↓
don't process again
```

That's called **idempotent ingestion**, and we'll build this properly later.

# 12. Why `UUID`?

We used:

```python

```

instead of:

```text

3

```

UUIDs provide globally unique identifiers.

For a system that may eventually become distributed, UUIDs are often more convenient than relying exclusively on sequential database IDs.

It's not that integers are "bad"; it's simply a deliberate identifier choice.

# 20. Why 768?

Because **BGE-base-en-v1.5** produces 768-dimensional embeddings.

So:

```text
BGE
 ↓
768 numbers
 ↓
PostgreSQL
 ↓
vector(768)
```

The database needs to know the dimensionality because it performs vector mathematics.

You can't compare:

```text
vector(768)
```

with:

```text
vector(384)
```

as though they're the same space.

# 22. Why `nullable=True` on embedding?

You noticed:

```python
embedding = ... nullable=True
```

This is intentional.

Think about ingestion.

We may have:

```text
Document
 ↓
Extract
 ↓
Chunk
 ↓
Database record
 ↓
Embedding generation
```

Embedding generation could fail because:

* model unavailable
* GPU problem
* network issue
* model loading failure
* resource exhaustion

We don't necessarily want the entire document record to disappear.

So we can represent:

```text
chunk exists
embedding = NULL
```

and later retry embedding.

That's a useful production pattern for asynchronous/reliable indexing.

Eventually we'll probably have explicit indexing states too.

# 26. What does `cascade="all, delete-orphan"` mean?

Suppose:

```text
Document A
├── Chunk 1
├── Chunk 2
└── Chunk 3
```

If we intentionally delete the document, we don't want:

```text

Chunk 2
Chunk 3
```

floating around with no parent.

So:

```text
delete Document
      ↓
delete its chunks
```

That's what the relationship configuration helps enforce.

And our database FK also has:

```text

```

which you saw in PostgreSQL:

```text
FOREIGN KEY
(document_id)
REFERENCES documents(id)
ON DELETE CASCADE
```

# 31. Why `normalize_embeddings=True`?

This is a subtle but important part.

Vector similarity can be affected by vector magnitude.

Normalization transforms the vector so approximately:

```text
||v|| = 1
```

Then cosine-based comparison becomes easier and consistent.

Conceptually:

```text
vector
  ↓
normalize
  ↓
unit vector
```

Later we'll use cosine similarity/distance for retrieval.

# 36. What does PGVector actually do?

This is where your embedding knowledge becomes practical.

Suppose:

```text
Query:
"How does Redis recover after restart?"
```

gets:

```text
Q = [768 numbers]
```

Database contains:

```text
Chunk A → [768 numbers]
Chunk B → [768 numbers]
Chunk C → [768 numbers]
Chunk D → [768 numbers]
```

PGVector calculates distances:

```text
Q ↔ A = 0.18
Q ↔ B = 0.71
Q ↔ C = 0.22
Q ↔ D = 0.89
```

Smaller cosine distance = more similar.

So:

```text
A
C
```

are retrieved.

Then:

```text
A + C
```

become context for the LLM.

# 42. The interview explanation

If tomorrow someone asks:

> **"Explain your RAG architecture."**

Don't say:

> "I used LangChain and PGVector."

Say something like:

> "I built the RAG system as separate indexing and query pipelines. During indexing, documents are loaded, normalized and split into chunks. Each chunk is converted into a fixed-dimensional embedding and stored in PostgreSQL using PGVector along with document metadata and content hashes for deduplication. At query time, the user query is embedded using the same embedding model, and PGVector performs similarity search to retrieve the most relevant chunks. Those chunks are then assembled into context and passed to an LLM through the generation layer. I separated the embedding provider behind an interface so the retrieval system isn't coupled to a specific embedding model."

**That is the explanation I want you to eventually be able to give without looking at the code.**
